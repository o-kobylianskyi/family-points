## Mandatory portable recovery use case (expressly confirmed in user conversation)
**A recoverable user-held `.fpbackup` file must be sufficient to restore supported family-local data after total loss of the original server or database**, subject to a legitimate authenticated owner, explicit mapping into the appropriate target family and strict security checks. Do not require the old PostgreSQL to still exist. This is not authorization to recreate users or credentials or grant administrative permissions automatically. If the system cannot establish owner legitimacy or map historical members securely, it must provide an explicit blocked recovery state instead of an unsafe restore.

## What approval does *not* imply
- Does **not** mean technical ACK to an exact proposed field/DTO/migration is complete. Architecture should implement DEC-01…08 in detail, make conflict-resolution choices and record affected consumer ACKs; routine technical choices need not return to user unless product requirements change.
- Does **not** allow destructive testing of real user data, deployment, modification of production accounts, automatic owner enrollment, or lifting of `restorable=false`, `replaySupported=false`, Reset Execute HTTP 423 or BETA HOLD.
- Does **not** authorize an implicit cross-family migration/restore, merge, automatic user/password copying or guessed owner.
- Security/QA release gates require independent disposable PostgreSQL tests, full same-SHA non-skipped four-job CI and explicit deployment authorization.
