## Context
Existing task virtual schedules and multi-slot occurrence identity must be reused. RewardDefinition has prerequisite, purchase, reputation, cooldown, count-quota and duration rules but no acquisition-date schedule. See `docs/architecture/ADR-CAL-001.md` and inspect current code HEAD (do not trust this snapshot after other tracks commit).

## Delivery scope
1. Add backward-compatible reward availability model: ALWAYS default, ONE_TIME instant range, RECURRING_WEEKLY with multiple weekday/time windows and optional effective dates/enabled. No bulk reward instances. Choose additive Flyway revision **after inspecting actual latest migration number and CI branch**.
2. Explicit workspace IANA timezone strategy, deterministic Clock-based evaluator and DST/legacy LocalDateTime compatibility plan; do not silently change existing task penalties or quota timestamps. Document migration/default.
3. Manager-only reward schedule read/update contract, and computed availability for authorized member; older `PUT /rewards/{id}` missing schedule must **preserve** existing schedule, not reset it. Add structured response reasons and next eligible opening; no sensitive member data leaks.
4. Revalidate acquisition windows transactionally inside BOTH direct `RewardService.purchaseReward` and approved `purchaseRequest` before purchase creation/point spend. Preserve existing checks: requirements, request approval, reputation, cooldown, member/family quota, blocked obligations and balance. Open/close half-open window, never trust client clock.
5. Bounded, read-only `GET /workspaces/{workspaceId}/calendar?from&to&memberId...` unified projection. Preserve current `/tasks/members/{memberId}/schedule?date`, slot keys and histories. Use shared reward windows; do not write TaskInstances or RewardPurchases on reads. Guard N+1 and large month requests.
6. Audit workspace scoping, validation (overlap/overnight/disabled windows), default behavior and error codes. Agree DTO with Web and Android via IMP-0006 and record tested SHA in Backend journal.

## Explicit non-goals
Do not implement screen-time entitlement usage, extra-request one-time bypass, push notifications, holidays/RRULE, recurring task start-time semantics, or deploy BETA in this package.

## Acceptance criteria
- [ ] Old catalog rewards behave as ALWAYS; old create/edit clients cannot erase configured window accidentally.
- [ ] WEEKLY multi-windows and ONE_TIME date+time validate and preview correctly; DST/timezone edge cases exercised.
- [ ] At 15:59:59, 16:00:00, 17:59:59, 18:00:00 the server enforces expected [16:00,18:00) schedule for BOTH acquisition paths.
- [ ] A rejected purchase does not debit ledger, generate obligation or consume quota; race/replay/rollback tested.
- [ ] Regular task prerequisite + reputation + point balance + cooldown + quotas still enforced, regardless of window.
- [ ] Auth: no cross-workspace ID leaks; member visibility/permissions tested including another family's tasks and rewards.
- [ ] Calendar month query returns stable virtual task+reward events, existing instance status wins, no persistence writes; no future TaskInstances generated.
- [ ] Backend build, Flyway fresh/upgraded DB and relevant tests **actually run** with evidence; record compat requirements, commits, reviewer ACK and release risks.
