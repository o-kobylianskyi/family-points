## Екранний час — не автоматичне право

Ціни нагород TIME не обходять Family Link, обмеження ОС, дозволи дорослого, вікові вимоги, ліміти за добу/тиждень, доступність пристрою та фактичний таймер. Факт покупки / отримання нагороди **не запускає** таймер; лише фактичний початок споживання після перевірок.

## Повторні нарахування: контракт для Архітектора / Backend

1. Визначити ідентичність виконання як `workspaceId + taskInstanceId + participantId + earningEventType` (або еквівалент, погоджений із доменною моделлю). Унікальність забезпечує БД або транзакційний ledger, а не кнопка Web.
2. Повторна доставка однакової команди (з тим самим idempotency key) не створює нове нарахування. Результат повтору повертає первинний результат або стабільну відповідь «already processed».
3. Різні користувачі/пристрої, offline replay, повторне схвалення та race condition не повинні дублювати транзакцію.
4. Складені завдання/підзавдання потребують явної політики: або платиться тільки parent, або тільки children, або явна комбінація без перетину винагород.
5. Для щоденних/тижневих повторень потрібен окремий occurrence ID, щоб не блокувати законні наступні виконання.
6. Скасування помилкового нарахування — нова компенсуюча ledger-подія з аудитом, не переписування історії.
7. Можлива винагорода групі та індивідуальному учаснику має мати явно відмінні beneficiary і політику розподілу.
8. Ліміти на задачі/день/тиждень мають бути окремими налаштуваннями, не припускати глобального cap без договору.
9. Створення й оплата нагороди — окрема idempotent операція; баланс не може зменшитися двічі через подвійний тап.
10. Якщо нема стабільного ID offline-виконання, не схвалювати повторно «наосліп», а передбачити reconcile та повідомлення батькам.

**QA:** одночасне схвалення з двох пристроїв; повтор 3× одного ключа; офлайн replay після reconnect; різні keys на той самий occurrence; відхилення/повторна оцінка; конкуренція parent/child; баланс = сума ledger; обмеження часу попри достатній баланс.

## Рішення перед реалізацією

- Погодити, які саме нагороди можна оплачувати балами, і чи слід сімейні взаємини взагалі відображати як REWARD.
- Протестувати справедливість цін у кількох сімейних профілях, не монетизуючи базові права.
- Уточнити доменні ID для idempotency, group actor, scheduler occurrence, та API режим повтору.
- Зберігати рекомендовані значення як редакторські пропозиції, не мутувати встановлені індивідуальні параметри.
