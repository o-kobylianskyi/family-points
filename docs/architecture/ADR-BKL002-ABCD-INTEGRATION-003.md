## Binding producer/consumer interfaces — first reviewable contract stage

### A → B/D: `PortableSourceArchiveVNext` (logical interface, NOT final JSON/Java DTO)
- Source `workspaceId`, immutable `snapshotId`, content `schemaVersion`, `dataEpoch`, sealed source digest, explicit selected categories and category row counts/content digests.
- Separate authenticated original-member ancestry, source family role/type/active/deleted/tombstone state and all member-ID references; no global credentials. Historical original IDs are **source-graph references**, not target PK claims.
- Point type/rate/ledger/task/reward/member-group/media parent closure and all needed binary bytes; old schemas fail closed where proof absent.
- **A** owns concrete wire names/JSON/version and privacy-minimal fields; **B** must ACK exact required source fields and reject unsupported before A introduces runtime category changes.

### C → B: `OwnerApprovedRestorePermit` (logical interface, NOT an API already delivered)
- Cryptographically verifiable durable owner reauth result and target workspace authorized actor; action `RESTORE`, operation UUID, selected scope+source snapshot hash, reviewed exact member mapping hash, target epoch, expiry <=5min and unique nonce/key.
- Canonical shared lock order: target family/epoch lock **first**, then operation/permit row, then target category rows, with source-state checks and protected target backup before commit. The implementers must test actual DB lock ordering, and where backend audit/protection conflicts exist must escalate before merging.
- Consume permit and target data mutation in one transaction; do not treat synthetic actor IDs, local JVM hash sets or archive owner metadata as genuine permission.
- Reset permit `RESET` cannot be reused as RESTORE grant and vice versa.

### D → A/B/C: `FinancialClosureProof` (logical interface)
- Immutable signed source category source-type vocabulary, parent IDs, currency references, snapshot amount/rate and member ID ancestry. Verified exact mapped source ledger rows and per-member/per-currency sums, group/reputation/obligation where supported.
- No smoothing away invalid rows via same net balance; duplicate/out-of-scope/unknown source and unapproved REFUND/exchange semantics deny.

### B → Web/Android/QA: `RestorePreviewAndReceipt` (conceptual, not enabled)
- Read-only preview includes source/target category counts, preserved data, explicit conflicts, mapping, snapshot/epoch and deny reasons. Outcome uses durable operation ID and old/new epoch; lost POST reply recovered via GET receipt, no second application.
- No destructive client UI while execution disabled. Web/Android only adapt after Architecture IMP and QA.

## Order and parallelism (binding)
1. **NOW:** A continues source transaction/staging/crypto hardening without changing portable member wire; B continues TEST-ONLY target replay and FK maps; C continues explicit security proof/negative and reset preview with execute disabled; D continues signed finance parity and PG fixture test. QA checks same immutable SHA.
2. **First contract merge:** A publishes concrete vNext member/source graph; B and D ACK exact fields, C reviews owner/account privacy. Architect logs IMP and resolves any conflicts, then A can implement producer/inspector versioning.
3. **Authorization merge:** C publishes concrete verified-owner durable permit and legitimate legacy enrollment policy; B ACKs atomic consumption and lock order. No guessed owner backfill. Flyway migration only after review and independent test.
4. **Engine merge:** B integrates signed A archive + C permit + D financial validation into one protected transactional FULL/SELECTIVE restore, checks durable receipt and A/B source-target media/ledger parity; C separately builds dependency-safe Reset executor.
5. **Release gate:** independent QA synthetic PostgreSQL, approved disposable user-facing E2E, Web/Android epoch and offline QA, Release exact-SHA non-skipped 4-component CI, backup/restore rehearsal, formal authorization. No implicit BETA approval.

## Explicit out-of-scope/unsettled implementation details
- No generic MERGE, cross-family migration, auto-create logins or remote expiry of user backups.
- Exact wire field names, SQL tables/migration numbers, account-recovery UI and safe legacy enrollment evidence are implementation specs and QA acceptance subjects. Teams may design them within these rulings; **any proposed behavior that changes product policy or weakens fail-closed requirements must escalate**, not assume approval.
- User approval is not live destructive authorization. Until all gates: production `restorable=false`, `replaySupported=false`, Reset Execute HTTP423, **BETA HOLD**.
